# Diet redesign — implementation plan

**Status:** designed and approved 2026-10-18, not built yet. Replace this file with a
`DIET-LOGIC.md`-style description once it ships.

- **Designs:** Claude Design canvas "Diet — meals by time",
  https://claude.ai/artifact/AZGhAGWdzJD5iSXuYTdrDU. Round 3 (top row) is the logging
  flow (Meal page, New meal, Amount, Scan, New product); round 2 is the locked
  timeline (Timeline, Meal card option 1, Other days).
- **Components and rules:** the Protocol design system (link in `CLAUDE.md`), group
  "Diet": `DayStrip`, `DayTotals`, `MealCard`, `MacroTable`, `AmountInput`,
  `UnitList`, `Scanner`, plus the README's Diet section.
- **Users:** Peki and their sister first; it must work for anyone, so no macro is
  promoted for one person's needs.

## Decisions

- **A meal is whatever you ate at one time.** No breakfast/lunch/dinner slots. The
  day is a timeline of meals by time, under a week strip and the day totals.
- **Kcal and protein lead everywhere; carbs and fat are always shown** next to them:
  per day, per meal and per food.
- **Logging is by meal, one food at a time.** "Log meal" opens a new meal at the
  current time. The search box adds the next food only: pick a result, set the
  amount, it joins the meal's list and the search clears. To add more later, open
  the meal and add again. No multi-select.
- **Meals are named by Claude Haiku** ("Protein salad", "Apple", "Snack") and marked
  AUTO until renamed; a rename always wins. Haiku also groups long ingredient lists
  into 2–3 lines for the timeline card. The meal page lists every food.
- **Amounts are a unit plus one typed number.** Every food has grams plus its own
  units (cup · 91 g, floret · 11 g, cookie · 12 g, pack · 200 g). The grams
  equivalent shows under the number when the unit isn't grams. A logged food keeps
  its unit and number, so it reopens as "3 cookies".
- **Products come from the pack.** The scanner is the camera plus an exit. A known
  barcode (our foods or Open Food Facts) opens Amount; an unknown one opens New
  product with the code attached: photos of the front and the nutrition table,
  Claude reads name, brand, per-100 g values and units, everything editable, then
  Save → Amount.
- **Other days:** the chrome's arrows step a day, the week strip shows each day's
  kcal against target, the title opens a month calendar. Past days are editable.

## Data model

No backwards compatibility: replace, migrate, delete the old shapes.

- **`meals`** (new): `id` (UUID, generated by the client), `user_id` (FK, cascade),
  `eaten_on` (DATE, the user's local date, as `food_logs.logged_on` is today),
  `eaten_at` (TIME, local wall clock), `name` (nullable), `name_source`
  (`auto` | `user`), `summary` (JSONB, nullable: Haiku's `[{text, grams}]` lines),
  timestamps. Index `(user_id, eaten_on)`.
- **`meal_items`** (replaces `food_logs`): `id`, `meal_id` (FK, cascade), `position`,
  `food_item_id` (FK, SET NULL), denormalized `name`, `unit_name` (nullable = grams),
  `unit_quantity`, `quantity_g`, `kcal`, `protein_g`, `carbs_g`, `fat_g`. Items keep
  their own name and macros so they survive edits or deletion of the food.
- **`food_units`** (new): `id`, `food_item_id` (FK, cascade), `user_id` (nullable:
  NULL = shared, from a label or seed data; a user id = that user's own unit, allowed
  on any food they can see), `name`, `grams` (> 0). Unique on
  `(food_item_id, user_id, lower(name))`. Visible units = shared + the user's own.
- **`food_items`:** drop `default_serving_g`; it becomes a shared "serving" unit
  (convert `seed_data/foods.json` and existing rows in the migration).
- **Migration:** create `meals`, `meal_items`, `food_units`; move each user's
  `food_logs` into one meal per `logged_on` at 12:00 with no name (prod had no food
  logs on 2026-10-18; dev databases may); convert `default_serving_g`; drop
  `food_logs` and the column. Extend `tests/test_migrations.py` with a populated case.

## API

- `GET /api/meals?date=YYYY-MM-DD` → the day: totals, targets, and meals (time,
  name, name source, summary, totals, items).
- `GET /api/meals/days?from=&to=` → `[{date, kcal}]` for the week strip and calendar.
- `PUT /api/meals/{id}` → full snapshot `{eaten_on, eaten_at, name?, items[]}`,
  idempotent upsert, owner-checked (another user's meal → 404). Sending `name` sets
  `name_source = user`. Full snapshots match workout sessions and let meals go
  local-first later without an API change.
- `DELETE /api/meals/{id}`.
- `GET /api/foods?q=` → the user's recently used foods first, each with `last_used`
  `{unit_name, unit_quantity, quantity_g}`; every food carries its visible `units`.
- `POST /api/foods` accepts `units`. `POST /api/foods/{id}/units` and
  `DELETE /api/foods/{id}/units/{unit_id}` for the user's own units (and shared
  units on foods the user may edit).
- `POST /api/foods/read-label` (multipart, 1–4 images) → a draft `{name, brand,
  per_100g {kcal, protein, carbs, fat}, units [{name, grams}]}`. Saves nothing.
- `GET /api/foods/by-barcode/{code}` stays as it is.
- Remove `/api/food-logs`.

## Claude

- Add the `anthropic` package; key in `.env` as `ANTHROPIC_API_KEY`
  (`settings.anthropic_api_key` already exists). Without a key the app still works:
  meals show their food names joined, and New product is filled in by hand.
- **Meal name and summary:** when a meal's items change, a background task sends the
  item names and grams to `claude-haiku-5-5` and asks for structured output
  `{name, lines: [{text, grams}]}`. Store `summary` always; replace `name` only while
  `name_source = auto`. About $0.00007 per meal.
- **Label reading:** a vision call with the photos, structured output as above,
  converting per-serving values to per 100 g when that's all the label gives, and
  turning "per cookie (12 g)" and the net weight into units. Model: Opus 5.5 by
  default (~1–2 cents per product); Haiku 5.5 is the cheaper option to try. Decide
  when building.
- Load the `claude-api` skill before writing this code.

## Frontend

- **`pages/Diet.tsx`** (rewrite): chrome with day arrows, title opens the calendar
  sheet; `DayStrip`; `DayTotals`; the timeline of `MealCard`s; "Log meal" floating
  pill → `/diet/meals/new`.
- **Meal page** `/diet/meals/:id` and `/diet/meals/new`: chrome (eyebrow
  `MEAL · SUN 18 · 13:30`, title = name, ⋯ menu with "Log again today" and
  "Delete meal"); meal totals; Name row (AUTO tag, rename) and Eaten-at row (time
  input); `MacroTable` (rows open Amount to change or remove); "Add the next food"
  search with a scan icon inside, results → Amount sheet; "Not in the list?" →
  New product; Done. A new meal gets a client UUID and is saved with its first food.
- **Amount sheet:** `AmountInput` (unit pills incl. "+ unit", one decimal field with
  −/+, grams line, live macros), "Add to meal" or "Save" + "Remove from meal".
- **Scanner:** cut `BarcodeScanner.tsx` down to the camera, the frame and an exit (no
  typed code).
- **New product** `/diet/products/new?barcode=`: photo slots
  (`<input type="file" accept="image/*" capture="environment">`, downscaled before
  upload), barcode row (scanned / rescan), read-label → editable fields, `UnitList`,
  Save product → back to the meal with Amount open for it.
- **Calendar sheet:** month grid of day cells with the same kcal bar.
- **Delete** `AddFoodSheet.tsx`, the food-log hooks, query keys and types.
- **Navigation:** meal page's parent is Diet on that meal's day; New product's parent
  is the meal (`useBack`).
- **Offline:** first version online with optimistic cache updates; local-first meals
  (drafts + queue as in `lib/workoutSync.ts`) as a follow-up.

## Tests

- Backend: the migration (food logs → meals, serving → unit); meals API (PUT
  idempotent, ownership, day totals, days range); unit visibility (shared vs own);
  search ranking; naming and label reading with the Anthropic client mocked.
- Frontend (vitest): amount maths (unit × grams → macros), meal and day totals, the
  fallback meal name.

## Open questions

- Where the bodyweight card goes (today it sits under the food list).
- Should anyone be able to correct a shared barcode product? Today the first
  submission wins and nobody can fix a typo. Suggested: any user can edit barcode
  products; seeded foods stay read-only.
- Label-reading model: Opus 5.5 or Haiku 5.5.
- Quick add (numbers without a food) and describing a whole meal to Claude are not
  designed.
- Search covers our own foods only; Open Food Facts text search was unreliable
  (503s) when tested.
